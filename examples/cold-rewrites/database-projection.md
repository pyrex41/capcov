# Database track: a first Futamura projection

**Public builder prompt.** Implement an interpreter `I(program, input)` for the engine card's declared fragment, then a repeatable specializer `S(I, program) -> executable(input)`. The law is `run(S(I, p), d) == I(p, d)` for supported `p` and dynamic `d`. Let Astra build the interpreter and staging machinery, not hand-write a kernel for each benchmark. Accept a new supported program after the build with no LLM call, source edit, or benchmark-specific template. A staged interpreter with shared operation definitions is sufficient. A separately hand-coded IR compiler is a useful comparator, not by itself evidence of interpreter specialization. No self-application or second/third projection required.

Retain interpreter source, binding-time split, static input, generated code/IR and build receipt. Show what disappeared (dispatch, type tests, column lookup) and what remains dynamic. Include specialization identity: static program, types/schema, semantics flags, generator/toolchain versions and target architecture. Refuse unsupported inputs and invalidate on incompatible changes; do not treat fallback as a specialized success.

**Private evaluator prompt: correctness before speed.** Use the [shared Capcov protocol](README.md) to freeze programs, fixtures, omissions, and budgets. Run *three* paths: pinned upstream engine, generic interpreter, and residual executable. The first comparison checks source compatibility; the second checks specialization. Replay the exact same logical program, data, parameters and initial state; retain typed results, errors, ordering when contracted, and externally observable state after transactions. Test novel programs as well as novel data for known programs. A deliberately changed result must fail comparison. Capcov receipts are scoped evidence, not a proof for arbitrary queries.

**Private performance prompt.** Before sampling candidates, pin hardware, compiler flags, versions, threads, memory limit, datasets, durability, warm/cold definitions, repetition count and a decision threshold. Time outside Capcov's tracing/serialization path; validate output hashes separately. Benchmark the generic and specialized paths over the same physical representation and operator implementations. Report the native engine as an independent end-to-end baseline, not as the denominator for claiming that specialization worked. Don't compare an in-memory kernel against SQL parse + disk I/O without labeling the scopes.

Separate preparation, specialization/build, first invocation, warm execution, and end-to-end elapsed time. For each workload record throughput, latency distribution, peak memory, residual code size, and raw paired samples (randomized order, multiple independent processes). Report uncertainty across runs. Break-even reuse count is approximately `ceil(extra preparation cost / per-call saving)` when saving is positive; otherwise it never amortizes. Include one-shot queries, repeat-heavy workloads, and enough distinct programs to expose compilation/cache pressure. Do not silently drop mismatching, unsupported or slower cases. Publish separate semantic and performance dispositions. A correct specialized program that loses to the generic interpreter is a valid negative result.
