# SQLite replication: specify the acknowledgement before the hook

Design prompt, not an implementation, proof, or availability promise. This is a sibling to the [query VM projection](sqlite.md), not another opcode. Keep stock SQLite's pager, locking and recovery. Use one database in WAL mode on a local filesystem per node; exclude ATTACH, alternate journal modes, shared network filesystems and direct unmanaged writers initially. Pin SQLite, VFS, sync settings, filesystem and crash assumptions.

## Decide which product is under test

1. **Archive and restore.** Litestream-style asynchronous WAL capture, snapshots and immutable segments. SQL commit success means local success. Track a separate contiguous remote recoverable prefix; a suffix may be lost with the primary. No elections, automatic promotion or zero-loss SLA. A VFS shim is a design option, not a claim about Litestream's implementation.
2. **Replicated commits.** A single logical writer, 3 voting nodes, crash/recovery faults, honest storage that honors sync, durable quorum commit and fenced epochs. Use an existing replicated-log implementation. Clients submit writes through a managed endpoint and cannot interpret raw local COMMIT success as quorum success. No new writes without a majority. Promise linearizable reads only through a separately specified current-leader read barrier plus local apply; label follower reads with their applied index. Byzantine behavior and correlated loss of a quorum's disks are out of scope.

## Evaluator prompt: formalize the hard boundary first

Write one authoritative protocol model (TLA+/TLC is a good default) for the second product. Distinguish proposed, durably replicated, consensus committed, locally applied and client acknowledged. Represent ordered entries, transaction/request identity, payload identity, leader epoch, per-node durable log and applied prefix, snapshot base and retained suffix. Treat commit authority as an explicit consensus interface with stated assumptions, not a majority count over arbitrary writes. Model partitions, duplicate/delayed messages, process death and loss of volatile state, retries after lost responses, and snapshot installation interrupted by crash. Model liveness separately under eventual connectivity, stable leadership, fair delivery and functioning storage; do not promise deadlines from this model.

Check at least: all applied histories are prefixes of a single committed history; a successful acknowledgement survives recovery from the promised failures; a retried request ID returns the original outcome or rejects a conflicting payload; an old leader cannot publish a conflicting committed entry; readers never see a partial transaction; a snapshot plus its retained suffix recovers the same logical state. Start with 3 nodes, 2 epochs, 2 clients and short logs. Save model configuration, explored bounds and traces. Include negative controls: acknowledge on local sync alone, or discard the old snapshot before the new one is durable. Require an actual counterexample to the corresponding invariant. Passing finite TLC exploration is not an unbounded protocol proof.

## Implementer prompt: make the native refinement observable

First build a pass-through observer for a pinned real SQLite build. Trace file identity, WAL writes/syncs, locking/shared memory, commit markers, checkpoint/restart and recovery. WAL frames may arrive in pieces; offsets are reused and a sync is not a SQL transaction or consensus decision. Bind segments to DB identity, generation, checksums, commit boundary and predecessor; retain a pinned consistent snapshot until dependent segments are safe. Reject gaps, torn frames, stale generations and incompatible page sizes. Do not upload by blocking on network I/O inside every xWrite.

Before quorum mode, demonstrate isolation of speculative local work: e.g. a private writer produces validated transaction batches, a consensus service orders them, and only committed batches are published to read-serving state. Specify how the next writer starts from the committed prefix and how snapshot installation and local apply are atomic and restartable. Do not just add Raft after an externally visible SQLite COMMIT. Do not assume a raw WAL is portable across independently checkpointed files. Define the exact replay baseline or choose a logical replication representation and constrain nondeterministic SQL. Persist dedup outcomes atomically with application state or reconstruct them from the committed log. If any mapping from a native event to a model action is ambiguous, record a refinement gap.

## Specialization and Capcov prompt

Use [semantic-co-design's durable job example at 92e6bae](https://github.com/pyrex41/semantic-co-design/tree/92e6bae9b3d1b0499bb337a583e950cc6b0307f8/logic) as a precedent for compiling local transition specs, not as distributed evidence. Specialize a Shen **or** Maude interpreter to the static protocol/version, record layout and apply rules. Keep terms, votes, durable acknowledgements, indexes, payloads and I/O results dynamic. Compare interpreted and native decisions on identical model traces; never specialize away a runtime durability check. Defer a second spec language until it supplies an independent check worth maintaining.

Drive actual processes via Capcov fixtures. Record client invocations and completions (including unknown outcomes), leadership, commit/apply indexes and post-restart SQL observations. Use deterministic fault barriers, not sleeps. First witness: client receives success, leader dies before followers apply, survivors elect a leader, client retries the same ID, then reads. Require one committed effect and the same outcome. Repeat with response lost and old leader isolated. Record schedules, binaries and seeds; replay reduced witnesses on generic and specialized paths. For archive mode instead cut power at capture/checkpoint boundaries and restore solely from archived bytes; report recovery point and restore time. Process kill is not power loss: use separate torn-write/sync fault injection if claiming that coverage.

Only benchmark runs meeting the declared semantics: stock local SQLite for local overhead; generic versus residual protocol engine at *identical* durability/quorum settings for specialization benefit. Measure throughput and p50/p99 acknowledgement latency, sync/network wait, apply lag, restore/failover time, and compilation amortization. If sync or quorum RTT dominates, that is a useful result. Gate progression: reproducible archive restore → model plus negative controls → instrumented quorum prototype with checked histories → fault campaigns → performance. Do not ship failover on the strength of the archive milestone.
