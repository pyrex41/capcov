v1 semantics in one paragraph. A command runs its actions as one transaction
(`caps.run`, `system.shen:147-157`): every action sees the transaction's
intermediate state, `publish` appends `[emit Kind V]` to the transaction's
effects (`system.shen:67`), and a failed `require`, a missing row or a broken
invariant rejects the whole transaction. A request names an observed outcome,
and `caps.admissible` (`system.shen:159-166`) maps it to the alternatives an
observation must be one of:

| Request outcome | Model commits `(S', E)` | Model rejects |
|---|---|---|
| `committed` | `{(S', E)}` | `{}` |
| `rejected` | `{}` | `{(S, [])}` |
| `aborted` | `{(S, [])}` | `{(S, [])}` |
| `unknown` | `{(S, []), (S', E)}` | `{(S, [])}` |

`unknown` therefore has at most two alternatives, resolved inside its own
transition. That is sound only because `publish` commits with the transaction:
the **atomic-publish assumption**, today implicit.

### 4.1 Outcomes

An invocation `x` of operation `O` with arguments `a` completes with one
outcome. `Run(O, a, S)` is the set of complete executions of `O` from state
`S`; each ends `committed(S', J)` or `rejected(L)`. An execution is a sequence
of **commit points**: a transaction commit, a delivery claim, an attempt send
(section 4.3). `Adm(x)` is the set of `(state, journal)` alternatives an
observation of `x` must be one of.

| Outcome | `Adm(x)` | A checker may conclude | A checker may not conclude |
|---|---|---|---|
| `[ok]` | every `committed(S', J)` in `Run` | `x`'s transactions committed; its deliveries took one of their response branches | that an attempt with response `info` landed, or did not |
| `[fail [rejected L]]` | `{(S, [])}` if every execution rejects with `L`, else `{}` | `x` changed nothing and emitted nothing; the model rejects with `L` | anything about other invocations |
| `[fail [rejected]]` | as above, any label | as above | the label |
| `[fail [aborted]]` | `{(S, [])}` whatever `Run` does | `x` changed nothing | that the model would have rejected, or committed |
| `[info]` | `{(S, [])}` ∪ every prefix, at commit points, of every committed execution, each sent attempt landed or not | `x`'s effects, if any, are one of these alternatives; an observed effect of `x` is real | that `x` had no effect; that its effects precede any later read; any one alternative chosen for convenience |

`fail` means nothing happened. Rejection is possible only in the precondition
or the first transaction; after a commit point the invocation cannot truthfully
complete `fail` (rule R-LATE-REJECT, statically; a run-time rejection there,
such as `update` of a missing row, is reported as the model defect
`late-rejection`). A real system that errors after a commit point must be
recorded `info`, as the faults default classifier does.

Negative: `rejected-history-unknown-outcome.ops-v2` (T-outcome);
`rejected-late-require.ops-v2` (R-LATE-REJECT); M3 (`ok` reported for an
`info` send that did not land: `Adm(ok)` excludes it, mismatch).

### 4.2 Intent and attempt identity

- **Intent.** `[intent X]` on an operation, an outbox record or a delivery.
  `X` uses only `literal`, `argument`, and `row-key` inside `for-each`
  (R-INTENT-SCOPE), so a retry with the same arguments has the same intent and
  the intent never depends on state. `[per-attempt]` (v1 bridge only): the
  intent is the invocation id.
- **Attempt.** Not syntax. The attempt id of a step is the invocation id
  joined with the step's name, `Inv/step` (step names unique per operation,
  R-NAMES; action names are a separate namespace, as in v1). A history's
  `invoke` supplies `Inv`; a retry is a new invocation, so a new attempt.
- **Effect record.** `[effect I A L]`: intent `I`, attempt `A`, logical effect
  `L`. Every journal entry is one record. Transaction effects carry the
  operation's intent and the transaction's attempt id.
- **Duplicate.** For a channel kind `K` declared `[at-most-once]` and intent
  `i`: two or more journal entries `[effect i _ [delivered K _]]` ⇒
  `effect_applied_twice(K, i)`. Entries count by journal position, not by
  value. Equal payloads under different intents are not a duplicate (M2);
  different payloads under one intent are. Under `[at-least-once]` repeated
  deliveries are not a violation.

A checker may count delivered records per `(K, i)` from observed entries as a
lower bound and conclude a duplicate from two of them, gaps or not. It may
not identify intents by payload, and may not conclude "at most one" from a
journal with an unobserved range (4.5).

Negative: `rejected-effect-without-intent.ops-v2` (T-outbox);
`rejected-intent-reads-state.ops-v2` (R-INTENT-SCOPE);
`rejected-retry-without-attempt-identity.ops-v2` (R-RETRY).

### 4.3 Transactions, outbox records, delivery attempts

- `[outbox-table T Kind]` declares table `T` with fields `payload` and `state`
  (`pending` | `in-flight` | `delivered`), keyed by intent id. Rows are
  created only by `[outbox ...]`; `insert` and `remove` never name `T`;
  `update` of `T` writes only `state` (R-OUTBOX-TABLE). Every outbox-table
  kind has exactly one `[channel Kind Contract]` (R-CHANNEL).
- `[outbox T [intent X] V]` is a **transactional** action: inside its
  transaction it inserts row `i = ⟦X⟧` with `payload ⟦V⟧`, `state pending`,
  and appends `[recorded T i ⟦V⟧]`. Write set `{T}`. Rejects
  `duplicate-key` if the row exists, like `insert`.
- `[transaction N As]` is a step: `As` (v1 actions except `publish`, plus
  `outbox`; T-action-v2) commit or reject as a whole; commit is one commit
  point, followed by the invariant check.
- `[deliver N T [intent X] [ok Ok] [fail Fail] [info Info]]` is an
  **external, non-transactional** step. With `i = ⟦X⟧`, row `r = T[i]`, and
  `Eligible` = `{pending}` for an at-most-once channel, `{pending, in-flight}`
  for at-least-once:
  1. If `r` is absent or `r.state ∉ Eligible`, the step does nothing.
  2. **Claim**: commit `state := in-flight` (a commit point; record
     `[effect i Inv/N [put T i "state" "in-flight"]]`).
  3. **Send** attempt `Inv/N` with `r.payload` (a commit point).
  4. The environment chooses the response. `ok`: the attempt landed before
     the response (`[effect i Inv/N [delivered Kind payload]]`); run `Ok`.
     `fail`: it never lands; run `Fail`. `info`: it lands at any later point,
     including after the final read, or never; run `Info`.
  All three arms are required (T-deliver).

An **attempt lands at most once**. A service that applies one request twice
(`ApplyTwice` in `capcov.faults`) breaks this; the draft has no syntax for it
(Q2).

**`info` send, at least three alternatives.** `send` of
`transfer-outbox.ops-v2` from job `j` pending, no outbox row. Writing
`(job status, outbox state, delivered records for j)`:

| Alternative | State | Journal suffix | Class |
|---|---|---|---|
| a0 | `(pending, —, 0)` | none | nothing |
| a1 | `(queued, pending, 0)` | recorded, put queued | outbox-only |
| a2 | `(queued, in-flight, 0)` | … put in-flight (attempt sent or not; if sent, may still land) | outbox-only |
| a5 | `(queued, pending, 0)` | … put in-flight, put pending (`fail` arm) | outbox-only |
| a3 | `(queued, in-flight, 1)` | … put in-flight, delivered | outbox+delivered |
| a4 | `(queued, delivered, 1)` | … delivered, put delivered (`ok` arm) | outbox+delivered |

`Adm(info) = {a0, a1, a2, a3, a4, a5}`; `Adm(ok) = {a2, a3, a4, a5}` (complete
executions, one per response; under `info` response a2 has an open attempt);
`Adm(fail [aborted]) = {a0}`; `Adm(fail [rejected L]) = {}`, since `send` can
reject only in its precondition, which holds.

Negative: `rejected-outbox-into-plain-table.ops-v2` (R-OUTBOX-TABLE),
`rejected-outbox-without-channel.ops-v2` (R-CHANNEL),
`rejected-deliver-without-info-arm.ops-v2` (T-deliver),
`rejected-publish-in-intent-transaction.ops-v2` (T-action-v2),
`rejected-publish-outside-transaction.ops-v2` (T-operation).

### 4.4 Histories

`[history Es]`: `[open]` first, `[close]` last, once each; invocation ids
unique; each `[complete Inv O]` follows its `[invoke Inv Op Args]`, at most
once; an invocation without a completion is `info`, as `History.close()` does
(R-HISTORY).

- An invocation completed `ok` or `fail` has all its commit points between its
  invoke and its complete. Its attempts whose response was `info` may still
  land later.
- An invocation completed `info` stays **open until close**: each of its
  remaining commit points may occur at any later point, interleaved at commit
  points with later invocations, after any `[read]`, and after `[close]`.
- A **world** is an interleaving of all invocations' commit points consistent
  with the above and with real-time order, each transaction evaluated in the
  interleaved state. Exploration bounds worlds; exhausting a bound is
  `unresolved`, never a pass.

With sequential `ok`/`fail` invocations this is v1's per-transition semantics.
What it adds is late linearization of `info`, which v1 cannot express.

Negative: `rejected-history-without-close.ops-v2` (R-HISTORY); H3.

### 4.5 Observations

`[read [observation [cut Stores B D] Rows J]]`:

- `Stores`: the tables and channels read. `Rows` is the full content of each
  table in `Stores`; any other table is unknown.
- `B`: `[barrier Id]`: the reads are one consistent cut. `[no-barrier]`:
  they are not, and a judgment combining two stores is `unresolved`.
- `D`: `[drained]`: the deployment attests that no commit point or landing of
  any invocation of the history is pending (faults: `applied_closed`, no
  `pending` request). `[not-drained]`: pending events may still occur.
- `J = [journal From To Parts]`: positions `From..To` of the history's effect
  journal; every position covered exactly once by `[entry Seq E]` or
  `[gap A B]`; positions below `From` count as a gap (R-JOURNAL; a violation
  rejects the observation as malformed).

Rules, each a limit on what a checker may conclude:

- O1. A gap is unknown, never empty. A judgment that entries in a gap could
  change is `unresolved`. A judgment established by observed entries alone
  and not reversible by more entries (two delivered records for one
  at-most-once intent) stands.
- O2. Without a barrier, nothing combining two stores is concluded.
- O3. Without drain, an event of an open invocation or open attempt that is
  not observed is not absent; it may occur after the read.
- O4. Entries are distinct by position. Two equal records at two positions are
  two effects; an adapter that merges them leaves a position uncovered
  (R-JOURNAL).

Negative: `rejected-journal-merged-entries.ops-v2` (R-JOURNAL); H3, H4.

### 4.6 Retry, idempotency, frames

- `[retry C Max]`: after an invocation of `C` completes `info` or
  `fail [aborted]`, the environment may invoke `C` again with the same
  arguments: a new invocation, so new attempts, same intent; at most `Max`
  (canonical integer string, 1..16) re-invocations. Never after `ok` or
  `fail [rejected L]` (Q6). R-RETRY: `C` is declared and has `[intent X]`.
  Under `[per-attempt]` every retry is a new intent and no duplicate across
  retries can be stated.
- **Idempotency** stays a model pattern, as in `ledger.ops:9-14`; the probe
  showed it expressible (H5). Same key, same arguments: the replay branch
  commits no state change; outcome `ok`; journal entries only from delivery
  steps on eligible rows. Same key, different arguments:
  `fail [rejected "idempotency-conflict"]`, `Adm = {(S, [])}`, no debit.
  Response values are not modeled, so "replay returns the original result" is
  only "same outcome, no state change" (Q4).
- `[disjoint A B]`: R-DISJOINT holds when `W(A) ∩ (R(B) ∪ W(B)) = ∅`,
  symmetrically, and no invariant reads both a table in `W(A)` and one in
  `W(B)`. `R` and `W` are the access summaries of `caps.analyze`
  (`system.shen:192-216`) extended: `outbox T` writes `T`; `deliver N T` reads
  and writes `T` and its arms' writes; invariant evaluation is not counted in
  `R` (unlike `caps.analyze`, which adds every table).

Negative: `rejected-retry-without-attempt-identity.ops-v2` (R-RETRY),
`rejected-disjoint-writes-outbox.ops-v2` (R-DISJOINT), H5.

### 4.7 Verdicts

Two judgments, each three-valued, each naming its executor class.

- **Conformance** of a history to a model: `matches` when some world is
  consistent with every observation and every observation is complete
  (barrier, drain, no gap); `mismatch` when no world is consistent with the
  observed facts (sound under gaps, since observed facts only add);
  `unresolved` otherwise.
- **Clause** over the worlds consistent with the observations, unknowns
  completed every allowed way: `violated` when the observed facts alone
  falsify it; `satisfied` when it holds in every such world; `unresolved`
  otherwise. Clause names are faults invariants where one exists:
  `effect_applied_twice(K, i)`; `unsettled_effect(T, i)` when outbox row `i`
  is not `delivered` (`violated` only at a drained, barriered read).
- **Model exploration** (no observation): a *finding* when some world within
  the bound violates the clause; otherwise "no finding within bound", never a
  proof.

### 4.8 Rules

`T-*` are datatype judgments in the draft; `R-*` are side conditions
(`capsv2.scoped?`, `capsv2.well-formed-history?`) or observation checks, none
implemented.

| Rule | Where | Rejects |
|---|---|---|
| `T-outcome` | `caps-outcome` | an outcome other than `ok`, `fail R`, `info` |
| `T-outbox` | `caps-action-v2` | an outbox record whose key is not `[intent X]` |
| `T-action-v2` | `caps-action-v2` | `publish` in a transaction of an operation with intent identity |
| `T-deliver` | `caps-step` | a delivery without all three arms `ok`, `fail`, `info` |
| `T-operation` | `caps-operation`, `caps-v1-steps` | a per-attempt operation with anything but one v1 transaction; any other operation without `[intent X]` |
| `R-INTENT-SCOPE` | `capsv2.scoped?` | an intent expression using anything but `literal`, `argument`, `row-key` |
| `R-NAMES` | `capsv2.scoped?` | duplicate step names, or duplicate action names, in one operation |
| `R-OUTBOX-TABLE` | `capsv2.scoped?` | `outbox`/`deliver` naming a non-outbox table; `insert`/`remove` on, or a non-`state` `update` of, an outbox table |
| `R-CHANNEL` | `capsv2.scoped?` | an outbox-table kind with no channel, or two channels for one kind |
| `R-LATE-REJECT` | `capsv2.scoped?` | `require` or `insert` in a transaction that is not its operation's first step |

## 6. Composition derivation and rejected examples

Judgment `{P} A {Q} ▷ W; E`: from `P`, `A` reaches `Q`, writing tables `W`,
appending effects `E` in order. Rules used (draft; the rule ledger and checker
are R04):

- P-update: `{Q[T.k.F ↦ v] ∧ exists T k} [update T K F V] {Q} ▷ {T}; [put T k F v]`
- P-insert: `{¬exists T k ∧ Q[T.k ↦ Fs]} [insert T K Fs] {Q} ▷ {T}; [create T k Fs]`
- P-outbox: `{¬exists T i ∧ Q[T.i ↦ (v, pending)]} [outbox T [intent X] V] {Q} ▷ {T}; [recorded T i v]`
- Seq: `{P} A {Q} ▷ W1; E1` and `{Q} B {R} ▷ W2; E2` give `{P} A;B {R} ▷ W1 ∪ W2; E1·E2`
- Frame: `{P} A {Q} ▷ W; E` and `tables(F) ∩ W = ∅` give `{P ∧ F} A {Q ∧ F} ▷ W; E`
- Conseq: strengthen the precondition, weaken the postcondition.

**Derivation: `core ; notify`** in the fresh branch of `transfer`'s `apply`,
where `core = funds; debit; credit; record` and
`notify = [outbox "transfer-outbox" [intent [argument "request"]] [argument "request"]]`.
Let `r` be the request.

1. From `ledger.ops`: `{P0} core {Q1} ▷ {wallet, transfer}; [put wallet from, put wallet to, create transfer r]`,
   with `P0` = precondition ∧ `¬exists transfer r` ∧ funds, and `Q1` =
   `exists transfer r` ∧ balances moved by `amount` ∧ `sum(wallet)` unchanged.
2. Invariant `outbox-follows-transfer` holds in the pre-state, so
   `¬exists transfer r ⇒ ¬exists transfer-outbox r`. Conseq:
   `{P0 ∧ F} core {Q1}` with `F = ¬exists transfer-outbox r`.
3. `tables(F) = {transfer-outbox}`, disjoint from `W(core) = {wallet, transfer}`.
   Frame: `{P0 ∧ F} core {Q1 ∧ F}`.
4. P-outbox with `Q = Q1 ∧ exists transfer-outbox r ∧ state pending`;
   `tables(Q1) ∩ {transfer-outbox} = ∅`, so `Q1` is framed through:
   `{Q1 ∧ F} notify {Q1 ∧ exists transfer-outbox r ∧ pending} ▷ {transfer-outbox}; [recorded transfer-outbox r r]`.
5. Seq on 3 and 4: `{P0 ∧ F} core; notify {Q1 ∧ exists transfer-outbox r ∧ pending}`
   `▷ {wallet, transfer, transfer-outbox}; [put, put, create, recorded]`.
6. Invariants after commit: `outbox-follows-transfer` from `exists transfer r`;
   `nonnegative` from `funds`. Transaction commit tags every record
   `(r, Inv/apply)`.

Why it is valid: the middle assertion of Seq matches after Conseq; both Frame
side conditions are checked on computed write sets; effects compose by
concatenation, keeping order and multiplicity (a set union would be M4); one
transaction gives every record one intent and one attempt. What it rests on:
the summary that `outbox` writes its table. Summarized like v1 `publish`
(empty write set, `system.shen:199`), step 3's side condition would still pass,
but R-DISJOINT would accept the claim in `rejected-disjoint-writes-outbox`;
that fixture is this mutant's test. The `deliver` step after `apply` is not
in the composition: it is past a commit point, and the `info` prefixes of 4.1
are exactly the cuts there.

**Rejected examples.** Each is a fixture in `v2-draft/` whose first line names
the rejecting rule.

| `rejected-retry-without-attempt-identity.ops-v2` | `R-RETRY` | retries of a per-attempt operation, each indistinguishable from a new request |

## 7. Compatibility: v1 `.ops` through the bridge

Elaboration `E`, applied to every v1 model:

- `[system N Ts Cs Ps]` ⇒ `[system-v2 N [[assume "atomic-publish-v1"]] Ts [] E(Cs) [] [] Ps]`.
- `[command N Args Pre As Post]` ⇒ `[operation N Args [per-attempt] Pre [[transaction "body" As]] Post]`.
- Request outcomes: `committed` ⇒ `[ok]`; `rejected` ⇒ `[fail [rejected]]`
  (v1 does not compare labels, `system.shen:160`); `aborted` ⇒
  `[fail [aborted]]`; `unknown` ⇒ `[info]`.
- Effects: v1 effect `L` of invocation `Inv` ⇒ `[effect Inv Inv/body L]`.
  Projection `π([effect I A L]) = L`.

**`atomic-publish-v1`**, a named, versioned assumption, declared by
`[assume "atomic-publish-v1"]` and required for any per-attempt operation
(R-ASSUME). It states: (A1) `publish` commits with its transaction; (A2) an
`info` outcome of a per-attempt operation resolves at its own position in the
history: no late linearization, no landing after a read.

**Claim.** For every v1 request with outcome `committed`, `rejected` or
`aborted`, `π(Adm_v2(E(req))) = caps.admissible(req)`: a per-attempt operation
has one transaction and no delivery, so `Run` has exactly the one execution
`caps.run` computes, and the rows of section 2 and 4.1 coincide. For `unknown`,
one transaction is one commit point, so the `info` prefixes are exactly
`{nothing, everything}` (`system.shen:165-166`), under A1 for operations that
publish and A2 for all. Argued, not executed: gate G5.

| Fixture | Commands | Publishing commands | committed / aborted / rejected | `unknown` → `info` |
|---|---|---|---|---|
| `outbox.ops` | `enqueue`, `send`, `ack` | `send` | identical | `{nothing, everything}` under A1, A2 |
| `outbox-intended.ops` | `enqueue`, `send`, `ack` | `send` | identical | `{nothing, everything}` under A1, A2 |
| `ledger.ops` | `transfer` | `transfer` | identical | `{nothing, everything}` under A1, A2 |
| `workspace.ops` | `create`, `rename`, `close`, `delete-account` | `create`, `close` | identical | `{nothing, everything}` under A1, A2 |
| `loop-completion.ops` | `close-all` | none | identical | `{nothing, everything}` under A2 |
| `loop-induction.ops` | `close-all` | none | identical | `{nothing, everything}` under A2 |

Consequence for the probe: a v1 fixture keeps its v1 answer. An IR-gap test
cannot flip on a v1 fixture without breaking this table; it flips on the v2
model (section 8).

## 11. Open questions

Design choices this spec makes provisionally or leaves open. None is settled
by the probe.

1. **Attempt identity.** Assigned by the semantics as `Inv/step`, or written
   in the model (a stored attempt counter, a message id the real system
   sends)? The draft assigns it; an adapter then needs a mapping from the real
   system's attempt identifier.
2. **One landing per attempt.** The draft assumes an attempt lands at most
   once. Should a channel be able to declare duplication of one attempt
   (`ApplyTwice`), and should that be an assumption or a channel property?
3. **`atomic-publish-v1` bundles two assumptions.** A1 (publish atomic) and
   A2 (info resolved in place) are independent; A2 is about histories, not
   publish. One name, as the plan states, or two?
4. **Response values.** Not modeled, so "replay returns the original result"
   is weakened to "same outcome, no state change". Model them?
5. **At-most-once and in-flight rows.** H3-drained shows the tradeoff: the
   intended model never redelivers an in-flight row, so an attempt with an
   `info` response leaves `unsettled_effect` until something reconciles it.
   Is reconciliation (query the receiver by intent) part of the intended
   model, and with what contract?
6. **Retry triggers.** Only `info` and `fail [aborted]`. Should a retry after
   `ok` be expressible (a client that retries on a slow `ok`)?
7. **Receiver contracts.** At-least-once with receiver-side dedupe by intent
   ("effectively once"): a third contract, or a clause on the receiver model?
8. **Drain granularity.** One flag for the whole deployment, or per store and
   channel, matching the faults completeness flags (`applied_closed`,
   `changes_closed`, `finals_closed`)?
9. **Late linearization bound.** Interleaving `info` commit points multiplies
   worlds. The bound and its reporting overlap R17; who owns it?
10. **Wire forms.** JSON shapes for v2 histories and observations, and the
    adapter protocol version that carries them (`capcov-scenario-adapter-v1`
    has binary choices and `{state, effects}` only).
11. **Intent namespace.** Duplicates count per `(channel kind, intent)`. Is an
    intent global, per kind, or per operation family?
12. **R-DISJOINT and invariants.** Excluding invariant reads from `R` and
    requiring no invariant to span both write sets is argued, not proved.
13. **Overlapping invocations.** Only `info` invocations overlap others in
    this draft. Concurrent in-flight `ok` invocations are R17's; does v2 need
    to admit them in histories before then?
